## 「NBA 封了家里宽带 IP」——更正：不是封 IP，是反爬认出了我们的请求

- 原先的判断错了。同一台机器（出口 `76.50.220.123`）上，用户自己的 Chrome 照常能打开 stats.nba.com / www.nba.com；
  被拦的是**像机器人的请求**：curl、Playwright 新开的自动化 Chrome（headed/headless 都一样）访问 www.nba.com 都 403（Akamai），
  Node fetch 当天早些时候连发一串后挂起超时，晚上再试又返回 200 JSON。所以是按请求头 / TLS 指纹 / 自动化标记 / 发送节奏判的，不是 IP 封禁。
- **判断解封看 stats 的 JSON，不看 www 的 403**：curl 打 www.nba.com 永远是 403，这说明不了任何事。正确的探针是
  用 `server/nbaClient.mjs` 发一个 `leaguestandingsv3` 请求，能拿到 30 行就是通的。
- 所有对外抓取（stats.nba.com、ESPN 伤病/比分/盘口）现在共用 `server/politeFetch.mjs`：
  macOS Chrome 156 的完整请求头（sec-ch-ua、sec-fetch-*，按站点给 Referer/Origin）、本次运行内的 cookie 罐、
  随机间隔（NBA 0.9–1.8 秒，ESPN 0.3–0.8 秒）外加每 10–20 个请求歇 5–15 秒、单次运行 / 单日请求上限、
  熔断（**第一次** 403/429、挂起超时、非 JSON 就停掉整次运行，冷却时间写进 `data/raw/fetch-state.json`，跨运行翻倍，封顶 24 小时）。
  熔断后要手动重试：确认已解封，删掉状态文件里对应站点那一项。
- ingest 的 NBA 请求走 `data/raw/nba/` 原始响应缓存：往季接口永不重抓，本季 1 小时内重跑不重抓（`NBA_CACHE_TTL_MIN` 可调）。
- 两种传输：
  - 默认 `NBA_TRANSPORT=node`：Node fetch + 上面那套请求头。**Node 的 TLS 指纹不是 Chrome 的**，只降低被认出的概率，不保证。
  - `NBA_TRANSPORT=chrome`：请求在一个真的 Chrome 里、www.nba.com/stats 页面内用 fetch 发（CDP，不依赖 puppeteer）。
    先 `sh scripts/nba-chrome.sh` 启动专用 Chrome（profile `~/.dc-nba-chrome`，端口 9223——日常 Chrome 已占 9222；
    不带 --enable-automation，`navigator.webdriver=false`），窗口别关，然后 `NBA_TRANSPORT=chrome node scripts/ingest.mjs`
    或 `NBA_TRANSPORT=chrome sh deploy/push-refresh.sh`。每次运行先加载一次统计页预热，整次运行复用同一个标签页。
- 2026-10-27 晚实测：node 传输 `leaguestandingsv3` 200、30 行；专用 Chrome 打开 www.nba.com/stats 正常（没有 403），
  chrome 传输同一接口 30 行。页面内 fetch 不能写 `credentials: 'include'`——stats.nba.com 的预检不给
  `Access-Control-Allow-Credentials`，会被 CORS 拦掉。
- 批量脚本（`pbp:fetch`、`lineups:fetch`、`impact:fetch`、`odds:history`、`books:fetch`）现在会撞上限：
  NBA 默认单次 200 / 单日 500，ESPN 单次 3000 / 单日 12000，用 `NBA_MAX_REQUESTS`、`NBA_MAX_PER_DAY`、
  `ESPN_MAX_REQUESTS`、`ESPN_MAX_PER_DAY` 放开，并自己承担被拦的风险。跑之前仍然先确认 `data/history/` 缓存齐全，别冷抓。
- 不做：代理/IP 轮换、验证码破解、轮换伪造 UA、指纹伪装库。

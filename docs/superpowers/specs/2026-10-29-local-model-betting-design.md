# 本地预测模型与三种下注思路（给用户选）设计 — 2026-10-29

## 意图

用我们自己的数据在本地训练比赛预测模型，目标是提高赢钱的机会，而不是只提高猜中率。三种思路都做，最后让用户自己选用哪一种。

用户原话：「我的意思是我们通过某个模型，建立一个本地的预测模型」「来预测比赛结果」「关键是投注的方式」「能不能增加我们赢钱的机会？」「1，2，3我们都做，我们给用户选择」。

「1，2，3」指设计者（Claude）提出的三种思路：
1. **找盘口的弱点**：模型不看盘口，按场景拆开找模型比盘口准的地方。
2. **盘口进模型**：把盘口价格也作为模型输入，让模型学什么时候该押。
3. **换市场**：除了独赢盘，也做让分盘和大小分。

以下除用户原话外，均为设计者的决定，标注「设计决定」的可由用户推翻。

## 对既定原则的改动（用户决定，需知悉）

项目原则是「模型不跟盘、不刻意反盘，盘口永不进模型」。思路 2 违背这条。用户这次的决定是「给用户选择」，所以本设计这样处理（设计决定）：

- **线上默认的预测（各页面的胜率、Elo、账本、影子模式）照旧不看盘口，不受本项目影响。**
- 思路 2 的模型只作为用户可选的「盘口参考模型」，在名称和结果卡上明确标注「使用了盘口」。
- 策略助手设计（2026-10-29-llm-strategy-assistant-design.md）里「不得有以盘口为条件的字段」不变。用户选思路 2，是选一个**模型**，不是在策略里写盘口条件。

## 诚实的预期

- 2022-23 起 4920 场（不含预热季 2021-22）：盘口收盘价的对数损失约 0.587，我们的 Elo 约 0.614。下注方式本身造不出优势，只能放大或保护已有的优势。
- 最有希望的优势，是伤病消息出来、盘口还没完全反应的时间窗口。之前的实验里，06:30 官方伤病报告让对数损失降了 0.0049，达到理论上限的 94%；但它的收益几乎全在赛季第 20 场以后。
- 最实在、但和模型无关的手段，是挑最好的价格（各家里选最好的赔率）。
- 很可能的结果是：三种思路都做完，没有一种在历史数据上有统计证据能赚钱。真出现这个结果，就照实告诉用户，不挑一个碰巧好看的数字。

## 目标

1. 一个本地模型训练与评估框架，按赛季往前推，三种思路共用。
2. **思路 1**：不看盘口的本地模型 L，以及在预先固定的场景里的下注评估。
3. **思路 2**：看盘口的模型 LM，与 L 用同一套特征加上盘口价格；下注评估方法相同。
4. **思路 3**：让分盘与大小分的回测引擎扩展（价格、结算），先用 L 的分差预测跑。
5. 每种思路都给出同一格式的结论：预测准不准（对数损失或分差误差）、下注有没有证据、试了多少次。
6. 通过的模型进影子模式做前向检验；无论通不通过，结果都能在策略助手里作为可选的「模型来源」使用（通不通过照实标注）。

## 非目标

- 不用神经网络、不用大模型做预测（数据量约 6000 场，太少）。
- 不做球员数据盘：没有历史价格。
- 不接真钱。
- 不改线上默认预测。要改，另走预注册加影子模式的流程。

## 反目标

- 先看结果再定场景、阈值、特征：所有可选项在看评估期数据前写死，登记在预注册文档里。
- 只报告最好的那个场景或思路，不报告试了多少个。
- 测试期 2025-26 参与任何选择。说明：2025-26 已被以前的分析看过，结论里照实标注；真正干净的检验靠前向影子。
- 把正的 CLV 当成赚钱的证据（开盘价情景平均 CLV +1.23 个百分点，ROI 仍为负，前车之鉴）。
- 思路 2 的模型被当成「我们的预测」显示在默认页面上。

## 数据切分（设计决定）

- 2021-22：Elo 预热，同时作为第一个训练季。
- 按赛季往前推：评估 2023-24 时用 2021-22～2022-23 训练；评估 2024-25 时用到 2023-24 为止；依此类推。
- **选择期** = 2023-24、2024-25：在这里选场景阈值、选模型超参数。
- **测试期** = 2025-26：每种思路只跑一次，跑之前冻结所有选择。
- 开盘价只有 2023-24 起才有：开盘价的评估沿用现有独赢盘回测 `server/betSplits.mjs` 的切分——2023-24 选阈值、2024-25 验证、2025-26 测试。
- **主价格用开盘价**（设计决定）：线上决定在北京 06:30 之后，收盘价已经含 06:30 以后的消息，用它回测会把结果说得太好、线上也复现不了。收盘价和最优价的结果只作敏感性分析，标注「收盘价含决策时点之后的信息」，不计入结论、不参与选择。

## 模型

### 特征（全部是赛前可得，设计决定）

| 特征 | 来源 |
|---|---|
| Elo 分差（分） | 现有 `server/lab.mjs` `replay` 的 `eloPts` |
| 主场 / 中立场 | 重放记录 |
| 休息差、两队各自是否背靠背 | 重放记录 `restRaw`、`b2bHome/b2bAway` |
| 阵容实力差：满员轮换价值 V(H) 的两队差 | 与 D_pre 同一套历史算法：上季收缩后的 IMP（`valuesUpto`）× 逐场滚动的满员轮换分钟（`injuryEloLab.mjs` 的 `healthyRotation`），只用当场之前的数据；不用线上的 `rotationMinutes.mjs` |
| 赛前伤病扣分 D_pre（两队各一） | 现有伤病报告历史（`data/history/injury-reports`）与 `injuryEloLab.mjs` 的 `preDeduction` |
| 赛季阶段：两队各自本季已赛场次 | 重放记录现在只有两队较小值 `teamGp`，需加 `gpHome` / `gpAway`（加法改动，不影响现有结果） |
| **（仅 LM）** 盘口去水后的主队胜率 | 开盘价（与下注价同一时点；去水方法同 `server/oddsMath.mjs`） |

伤病时点：特征按 06:30 那份报告算（设计决定：之前实验里它最好；且决定下注的时间也定在 06:30 之后，见「前向」）。开赛早于 06:30 的比赛沿用以前实验的做法，退回 22:00 那份（`scripts/injury-elo-lab.mjs`、`docs/injury-aware-elo-verdict.md`）。完全没有可用报告的（约 47 个队次，0.4%）D_pre 记 0，不另加标记特征。

### 模型形式（设计决定）

- **主模型**：带 L2 惩罚的逻辑回归，输出主队胜率。惩罚强度在选择期里用按赛季交叉验证挑，候选值预先写死（如 0.01、0.1、1、10）。
- **分差模型**（给思路 3 用）：同样特征的岭回归预测分差，再用逐季拟合的标准差换算成胜率或盖盘概率。
- 不做梯度提升树（设计决定：多一个模型就多一次比较；首版先看线性模型能不能过）。
- 训练在本地 CPU 上跑，Node 手写实现（项目不新增依赖；逻辑回归与岭回归可用现有 `fusionLab.mjs` 的线性代数）。
- 现在 V(H)、D_pre 的计算写在 `scripts/injury-elo-lab.mjs` 里；实现者把它们抽成可导入的模块，原脚本改为调用该模块，结果必须与原来逐场一致（测试）。所需历史数据 `data/history/impact_*`、`lineups_*`、`stints_*`、`injury-reports/` 本机齐全。

### 预测是否更准：通过规则（预注册）

- **L 对 P1**：P1 = 现有「Elo + 0.5·D_pre」，是目前最好的简单模型。在选择期两季合并，按比赛日分块 bootstrap，对数损失差的 95% 区间上界 < 0 → 通过。
- **LM 对盘口**：LM 的对数损失与盘口本身比；不要求通过，只报告（LM 含盘口，比盘口差就说明它没学到额外东西）。
- 通过后在测试期跑一次，报告结果，不改结论规则。

## 三种思路的下注评估

### 共同做法

- 下注规则沿用现有引擎（`server/betBacktest.mjs`）：B 类「优势 ≥ 阈值」策略，阈值候选 0.03、0.05、0.07（设计决定：只取三个，减少比较次数）；定额 1 单位。只在选择期挑阈值。
- 价格：结论只用开盘价。收盘价、最优价（各家中最好的价，现有 `closeBest` 情景）只作敏感性分析；最优价注明实际操作需要在多家开户。
- 结论用现有 `mlVerdict`：少于 300 注 → 样本太少；区间下界 > 0 → 有证据；否则无证据。
- 每个结论旁写明「本思路一共比较了几个组合」，并给 Bonferroni 校正后的显著性。校正按思路分别算（思路 1：6 个场景 × 3 个阈值 = 18 个组合；思路 2：3 个；思路 3：两种玩法各 3 个），报告末尾另列三种思路合计的比较数（设计决定）。
- 已知功效很低：开盘价只有约 2460 场选择期加验证期比赛，高阈值的格子多半不到 300 注，会写「样本太少」。这是数据量决定的，照实报告。

### 思路 1：场景（预先固定，设计决定）

只看这 5 类场景，外加「全部比赛」：
1. 伤病消息大：任一队 D_pre ≥ 2 分。
2. 背靠背：任一队背靠背。
3. 赛季初：两队已赛场次都 < 15。
4. 赛季中后段：两队已赛场次都 ≥ 20。
5. 模型和盘口分歧大：|L 胜率 − 开盘价去水胜率| ≥ 0.08。说明：这里盘口只用来挑场次，不进模型。

### 思路 2

不分场景（设计决定：LM 已经把盘口用进去了，再按场景拆就是重复比较），只在「全部比赛」上按阈值评估。

### 思路 3：让分盘与大小分

- 数据现状（已核实）：`data/history/odds_<季>.json` 每场只有一家公司，而且各季不是同一家（2022-23 是 Betfair 交易所，2023-24 Betfair 或 Caesars，2024-25 ESPN BET，2025-26 混有「Live Odds」滚球报价）。
  - 大小分：有大小分线 `total` 和赔率 `overOdds` / `underOdds`，覆盖 99% 以上的比赛。
  - 让分：只有让分线，**没有让分赔率**；`openSpread` 在 2022-23 全缺；`spread` 是收盘线还是滚球线不能确定。
- 处理（设计决定）：
  - 大小分照常回测。剔除来源是交易所或「Live Odds」的行；报告注明每季公司不同。
  - 让分盘的历史回测只作「参考，未验证」：赔率一律按 −110 假设，只用来源明确不是滚球的行，不出「有证据」结论。
  - 让分盘的真正检验靠前向：在现有赔率抓取里顺带解析并保存让分赔率（不增加请求），攒数据。
- 让分盘：用分差模型的盖盘概率，按优势阈值下注。
- 大小分：需要总分模型（同样的特征再加两队节奏和进攻效率；设计决定：首版用两队本季至今的场均总分与对手调整，实现者定细节），按优势阈值下注。
- 结算：赢、输、走盘（刚好打平退本金）。
- 没有多家价格，所以思路 3 不做最优价情景。

## 前向检验（影子模式）

- 通过「预测更准」规则的模型（L，以及思路 3 的分差模型）进影子模式：每天北京 06:30 那次运行（拿到官方伤病报告后）记录赛前胜率，并在同一行存下当时 `data/odds.json` 里的价格（独赢、让分、大小分及其赔率；现有影子表不存价格，新表要存），开赛后不可写，同法结算。
- LM 也进影子模式，但只记录，用作对照，标注「使用了盘口」。
- 评估节点与伤病版 Elo 影子模式一致：攒到 300 场看一次，常规赛结束再看一次。

## 给用户选择

- 策略助手的策略格式增加一个可选字段 `source`（设计决定）：`elo`（默认，现有模型）、`local`（L）、`local-market`（LM，标注「使用了盘口」）；以及 `market`：`moneyline`（默认）、`spread`、`total`。
- 每个来源在选择界面旁边固定显示它的结论（预测是否更准、下注有无证据、前向样本数），用户看着结论选。
- 这一步依赖策略助手先完成，**不在本项目范围内**，单独排期；本项目只负责产出模型、回测结果和影子记录，以及给策略助手调用的接口。

## 交付顺序（设计决定）

1. 训练与评估框架 + 思路 1（L）。
2. 思路 2（LM）：复用框架，只多一个特征。
3. 思路 3：先补让分盘、大小分的回测引擎（价格、结算、走盘），再接分差和总分模型。
4. 影子模式。
5. 接入策略助手的 `source` / `market` 选择。

每一步都有自己的预注册文档（照 `docs/superpowers/specs/2026-10-29-injury-aware-elo-prereg.md` 的格式）和结论文档，结论文档先给独立代理审阅。

## 约束

- 不改线上默认预测、账本、影子模式现有逻辑。新影子表只追加、开赛后拒写。
- 不新增 npm 依赖。
- 不新增抓取。只用已有的历史数据和现有定时任务抓的数据；遵守礼貌抓取规则，不碰 stats.nba.com 的批量请求。
- 沿用项目约定：node:test、中文注释、实验脚本放 `scripts/`、实验模块放 `server/*Lab.mjs`、结论放 `docs/*-verdict.md`。
- 上线（影子模式、策略助手接入）前打回滚标签、备份数据库，并等用户确认。

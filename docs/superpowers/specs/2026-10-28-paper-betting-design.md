# 模拟投注（纸面交易）设计 — 2026-10-28

## 意图

用户想知道：照我们模型的预测去美国主流博彩公司下注，会赚还是亏。用户可能据此决定晚上的真实投注。
所以这套东西的首要职责是**说真话**：给出有统计意义的盈亏证据，而不是好看的命中率。

用户原话：「用我们的结果来模拟到美国几个著名的投注网站进行投注」「看看我们的 performance」「这个要你来精心设计」「直接设计吧，你来定」。
以下除用户原话外，均为设计者（Claude）的决定。

## 目标

1. **历史回测**：在真实历史赔率上，按事先固定的规则模拟下注，按博彩公司分别、以及「挑最优价格」汇总，给出 ROI 与置信区间。
2. **前向账本**：从现在起每天开赛前记录模型选择与 DraftKings 赔率，赛后结算。记录只追加、不可改，是对模型最干净的检验。
3. **表现页**：在「预测总表」页加「模拟投注」区，顶部一句话结论。

## 非目标

- 不接任何真实投注账户、不下真钱、不做自动下注。
- 不爬博彩公司网站（反爬、地区限制、条款）；只用 ESPN 公开接口（`server/oddsClient.mjs` 已有的来源）。
- 不改线上预测模型（预测仍是生产 Elo）。
- 不做让分盘、大小分、串关。首版只做独赢盘（moneyline）——它和我们的胜率直接对应。

## 反目标（技术上能跑，但算失败）

- 在评估集上调门槛/规则，再报告同一集上的 ROI（过拟合出来的「盈利」）。
- 用赛后才知道的信息下注：赛后 Elo、收盘之后的价格、当前伤病勾选。
- 把小样本的正 ROI 写成「模型能赚钱」。页面结论必须带置信区间，区间含 0 就写「无证据表明能赢盘口」。
- 账本可被事后改写（补录、覆盖、删除）。
- 为了回测再去批量请求 stats.nba.com（家里宽带是唯一能抓 NBA 的出口，已被限流过一次）。

## 已知数据事实（2026-10-27 ESPN 采样，23 场）

- 端点：`sports.core.api.espn.com/v2/sports/basketball/leagues/nba/events/<id>/competitions/<id>/odds`（每场一次请求，返回多家 `items`）。
- 多家覆盖只在 **2021-22 ~ 2023-24**：DraftKings(40)、BetMGM(47)、Caesars(31/43/45/52/57)、BetRivers/SugarHouse(41)、Unibet(36)、ESPN BET(58，22-23 起)、Betfair(50)、PointsBet(48) 等。**FanDuel 任何赛季都没有。**
- 2024-25 只有 ESPN BET；2025-26 与 2026-27 只有 DraftKings(100)。
- 时点：2021-22、2022-23 多数只有 `current`（视为近似收盘）；2023-24 多数有 open/close/current；2026-27 已结束比赛有 DK `close`，未开赛只有 open/current，约开赛前 24 小时才出线。
- 噪声：每季都有 in-game「Live Odds」条目（如 −100000）；个别博彩商有离谱线（Caesars 一次 +2.5 vs 其余 +8.5）。
- 现有缺陷：`pickBook` 只认 DraftKings 新 id `'100'`，旧赛季 DK 是 `'40'`，回退到全为 0 的 priority 取第一条，所以 `backtest.json` 里 2459 场记成 Betfair（交易所，非美国博彩公司）。2021-22 在 `backtest.json` 无盘口。

## 设计

### 1. 历史多家赔率缓存（一次性抓取）

- 新脚本抓每场全部 `items`，存 `data/history/books_<赛季>.json`（gitignore，与其他 history 一致）。可中断续跑、已有则跳过。ESPN 每秒 ≤1 请求；五季约 7000 次，分批跑。
- 清洗：剔除 Live Odds、聚合源（accuscore/consensus/teamrankings 等）、与当场各家中位让分相差 > 3 分的条目；Caesars 多个 id 合并为一家。
- 每家每场取「最接近收盘」的价格：`close` > `current` > 跳过（不用 `open` 冒充收盘），并记录取的是哪个时点。
- 修 `pickBook`：DK 新旧 id 都认；`backtest.json` 的 provider 统计重新生成后核对。

### 2. 回测规则（事先固定，不在评估季上调）

- 模型概率：生产参数的逐场赛前 Elo 重放（`server/lab.mjs` / `server/fusionLab.mjs` 已验证与 `lab.replay` 一致），2021-22 只作 Elo 预热。
- 去水：同一家两边隐含概率按比例归一。
- **主规则（预注册）**：`edge = 模型胜率 − 该家去水胜率`，`edge ≥ 3%` 时在该方押 1 单位，按该家真实（含水）美式赔率结算。
- 对照（同样预注册、一起报告，不挑最好的报）：门槛 0% / 3% / 6%；「挑最优价」= 每方取各家最高赔率；「只押 DraftKings」。
- 门槛只允许在 2022-23 上看，2023-24 起只报告；文档写明。
- 指标：下注数、胜率、单位盈亏、ROI、按场 bootstrap 95% 区间、最大回撤、保本胜率（由平均赔率推出）。2023-24 有 open/close 的，另报 CLV（下注价 vs 收盘价）。
- 同时报告模型 vs 各家去水概率的 log loss / Brier，作为「为什么赚/亏」的解释。

### 3. 前向账本

- **存储**：线上排行榜那份 SQLite（`data-db/`，卷持久化，跨镜像重建保留）。新表 `paper_bets`，只插入；同一 (gameId, 规则, 博彩商) 唯一，重复插入忽略，不更新已有行的价格与选择。结算只写结算字段。
- **记录内容**：gameId、记录时间、模型胜率与所用赛前 Elo、DK 美式赔率与时点（open/current）、去水概率、edge、是否下注、方向；结算：比分、盈亏。
- **何时记录**：服务器 22:00（北京）cron 已在开赛前 9–12 小时，用它已抓的 scoreboard 赔率，**零额外请求**。可选再加北京 06:30（UTC 22:30，开赛前）一次，记录接近收盘的价格——这要改服务器 crontab，部署时单独征得同意。
- **结算**：14:30（北京）cron 时比赛已结束，用比分结算；顺带取 DK `close` 记 CLV（每场 1 请求，每天约 8 次）。
- 只用 DraftKings：2026-27 ESPN 只给这一家。页面写明。

### 4. 页面

在「预测总表」页加「模拟投注」区：
- 顶部一句话结论，由数据生成：例如「历史 3 季、N 注、ROI −x%（95% 区间 [a, b]）：无证据表明模型能赢盘口，不建议据此下注」。区间整体 > 0 才允许出现「有正收益证据」字样。
- 累计盈亏曲线（历史 / 本季账本分开）。
- 表：博彩商 × 门槛 的下注数、胜率、ROI、区间。
- 「今晚模拟下注」：今天账本里已记录的选择、赔率、edge；标注「模拟，不是建议」。
- 本季账本样本小时直接写样本量，不画结论。

### 5. 约束

- 不访问 stats.nba.com / nba.com。
- 不新增依赖。
- 中文注释与 UI；纯计算放可测的 server 模块，node:test 覆盖去水、结算、edge 规则、账本不可改写、清洗规则。
- 部署走 `deploy/README.md`；服务器 `docker-compose.yml` 与 `data-db/` 不覆盖；新表用迁移式 `CREATE TABLE IF NOT EXISTS`。

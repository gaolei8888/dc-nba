# NBA超级幻想

一个本地运行的 NBA 数据与比赛预测应用：涵盖 30 支球队的基础/高阶数据、全联盟球员数据、
2026-27 赛季完整官方赛程，以及基于 Elo + 效率评级 + 阵容影响力的比赛预测与赛季蒙特卡洛模拟。

## 快速开始

```bash
npm install
npm run ingest      # 从 stats.nba.com 抓取数据，约 45 秒
npm run backtest    # 在历史赛季上回测模型准确率（首次会抓 5 个赛季）
npm run odds:history # 抓历史收盘盘口（ESPN 公开接口，约 2 分钟，可选）
npm run impact:fetch # 抓 5 个赛季的 box+追踪+on/off（约 8.5 分钟，可选）
npm run lineups:fetch # 抓 5 个赛季的五人组合数据，用于算 APM（约 6 分钟）
npm run impact:fit  # 拟合并验证综合影响力指标 → data/impact-model.json
npm run dataset     # 把盘口并进实验室数据集（不重新抓 NBA 数据）
npm run check       # 检查 JSX 里的组件引用（build 会自动跑）
npm start           # 构建前端并启动服务 → http://localhost:5174
```

开发模式（前端热更新）：

```bash
npm run dev         # 前端 http://localhost:5173，API 5174
```

侧栏的 **「假设全员健康」** 是全局情景开关，与缺阵勾选一样对所有页面生效。

**开赛后界面只显示本赛季数据。** 球队、球员、积分、赛程（已结束的比赛带真实比分）
都换成 `TARGET_SEASON` 至今的数字；本赛季还没出场的球员显示为空，不会退回他上赛季的数字。
预测引擎仍以上赛季整季为基准（再加上本赛季已打的比赛滚动更新 Elo）——
几场比赛的样本撑不起评级。两套数字分开存：顶层字段是模型用的上赛季，
`t.cur` / `p.cur` 是展示用的本赛季，由 `server/index.mjs` 的 `showTeam` / `showPlayer` 在展示接口里替换。
**IMP 是例外，它必须用历史数据**：本赛季显示的 IMP =
`(20 × 上赛季 IMP + 本季场数 × 本季统计栏 SPM) / (20 + 本季场数)`，
上赛季 IMP 本身含近 3 季衰减 APM。上赛季没有 IMP 的人（新秀）仍要本季满 20 场才给分。
**K=20 没有验证过**（我们没有赛季内分段数据可回测），是按训练门槛取的。
它的代价看得见：约基奇开季 3 场 TS% 低于基准、对位被打出 +10%，
本季 SPM 是 −6.9，IMP 从 6.22 被拉到 4.51——这是真实的小样本噪声，不是 bug，
但 K 取大一些它就动得少。其余高阶数据（PIE、使用率等）按定义就是单赛季的，只显示本赛季。
人机对赌与模型实验室不受影响，仍用往季数据。

## 人机对赌

对已结束赛季的真实比赛做预测，跟模型比谁更准。

**模型的对手盘是无信息泄漏的。** `server/replay.mjs` 逐日重放上赛季：走到某场比赛时，
先记录模型的预测，再用真实结果更新 Elo。所以模型在每场比赛前掌握的信息和你一样多，
不存在"事后诸葛亮"。生成的题库落在 `data/gameday.json`（1230 场，含模型赛前判断与真实比分）。

**计分**：猜对得 `(信心 − 50%) × 200` 分，猜错扣同样的分。信心 55% 猜对得 10 分，
95% 猜对得 90 分、猜错扣 90 分。这样设计是为了让"下重注"只有在判断确实优于抛硬币时才划算。
另外同时算 Brier，与模型做同口径对比。

**存档在浏览器本地**（localStorage），服务端保持无状态、数据快照保持只读，
容器不需要挂卷。键名统一带 `dc-nba:` 前缀——作品与主站同源，
localStorage 按源隔离而不是按路径，不加前缀会和别的作品互相冲掉存档。

### 玩家档案：为什么没有账号密码

一台设备上可以建多个玩家档案，各自独立存档、可切换、可用存档码导出到别的设备。
身份被刻意做成「这台浏览器上的一个本地档案」，理由有三条：

1. 应用部署在 `/works/` 路径下，网关中间件双向剥离 Cookie，传统会话用不了，
   只能把令牌放 localStorage——安全性反而比 httpOnly cookie 更差。
2. 服务端无状态、快照只读、容器不挂卷。加账号就要加存储卷，
   随之而来的是备份、迁移、权限一整套负担。
3. 存密码是要负安全责任的，一个展示作品不值得。

**需要强调**：不同访客用各自的设备打开，本来就各玩各的，不需要登录。
登录真正解决的只有三件事——同一个人换设备接着玩、同一台设备多人分别存档、
跨用户排行榜。前两件用多档案 + 存档码已经覆盖，第三件需要服务端存储时再上，
届时 `web/src/lib/profiles.js` 里的 id + name 结构可以直接复用。

新赛季开打后，同一套机制会切到实时结算（ingest 会把已完成比赛带进来）。

## 服务端存储与性能

排行榜需要跨用户状态，这是整个应用唯一有状态的部分。

**SQLite（`server/db.mjs`）** — 用 Node 22 内置的 `node:sqlite`，不引 `better-sqlite3`，
省掉在 alpine 容器和 Windows 上的原生编译。三条设计约束：

- **写不进去要优雅降级，不能崩。** 容器以非 root 用户（uid 1001）运行，卷若归 root
  会 `SQLITE_READONLY`。启动时会真正写一次做探测，失败则记下可诊断的原因，
  服务端继续提供只读功能，前端退回纯本地存档。
- **绝不相信客户端报上来的分数。** 客户端只提交「押哪边、多少信心」，
  得分由服务端查真实结果自己算。实测提交 `points: 999999` 会被忽略，
  服务端按 conf 0.95 算出 90 分。
- **不存密码。** 身份用随机令牌（`Authorization: Bearer`），服务端只存 SHA-256 哈希。
  部署环境的网关双向剥离 Cookie，传统会话本来也用不了。

**性能（针对约 1000 在线用户）** — 实测数据：

| 问题 | 优化前 | 优化后 |
| --- | --- | --- |
| 20000 次模拟进行时，`/api/meta` 延迟 | 469 ms | **2 ms** |
| 赛程接口出口带宽（1000 用户，10 秒/请求） | 51.6 MB/s | **4.0 MB/s** |
| 混合请求吞吐 | 392 req/s | **516 req/s** |

三层处理，顺序有讲究：

1. **先消除工作**：模拟用固定种子，同参数必然同结果，直接缓存。
   大响应连压缩后的字节一起缓存，命中时零 CPU。
2. **再挪走工作**：缓存打不中的丢给 `worker_threads`（`server/pool.mjs`）。
   注意——**把同步计算包进 Promise 并不会让它非阻塞**，事件循环照样卡住，
   只有真正的工作线程才行。
3. **最后压带宽**：brotli/gzip，赛程压缩率 92.2%。1000 用户规模下
   带宽比 CPU 更早触顶，这一行比任何计算优化都值钱。

**排行榜是显式开关。** 它会在公网收集并存储用户数据（伪匿名令牌，无密码无手机号），
所以做成 `ENABLE_LEADERBOARD` 环境变量，仓库里默认 `0`——要不要上线是一条配置，
不是一次代码改动。关闭时服务端不写任何用户数据，前端自动退回纯本地存档。

**线上是开着的。** 高磊 2026-09-07 明确选择「开，不加备份」——是知情的选择，不是默认。
开关翻在部署副本的 `docker-compose.yml` 上并带了带日期的注释，服务器上那份配置自己就是记录；
仓库里保持 `0` 不变，这样谁都不会在本地跑起来就悄悄开始收数据。

**备份**：`npm run backup`（`scripts/backup-db.mjs`）。
**不能用 `cp`** ——WAL 模式下最新事务还在 `app.db-wal` 里，直接复制会拿到半截状态。
脚本用 SQLite 自己的 `VACUUM INTO`，在一致性快照上产出可直接使用的单文件，
不需要停服，也不需要容器里装 `sqlite3` 命令行。默认保留最近 7 份。

容器内的 cron 示例：

```
20 3 * * * docker exec dc-nba node scripts/backup-db.mjs >> /home/dev/work/works/dc-nba/backup.log 2>&1
```

两个会让备份**静默失效**的坑：

- **日志不要写 `/var/log/`**。那是 root 的目录，部署用的普通用户写不进去；
  而 cron 的 `>>` 重定向在命令执行之前就要打开文件，打不开则整条任务直接不跑，
  且不留任何错误。判断备份是否真的在跑，**看 `backups/` 里的文件日期，别看 crontab**。
- **镜像里只有 `scripts/backup-db.mjs`，没有整个 `scripts/`**。`ingest.mjs` 是抓取脚本，
  运行镜像里不该有它（`/api/refresh` 已关闭，抓取只在构建快照时做）。

**静态资源的缓存策略分两级**，搞错的后果很隐蔽：`index.html` 里引用的是带内容哈希的
资源名，浏览器一旦缓存住旧的 `index.html`，就会一直去加载旧的 JS——发了新版也看不到，
而且用户没有任何提示。所以 `assets/` 下的文件（名字本身带哈希）设 `immutable` 缓存一年，
`index.html` 设 `no-cache` 每次回源校验。

线程池挂掉会自动退回主线程计算，功能不因优化而失效。
`GET /api/health` 返回线程池状态、缓存条目数、内存占用，方便压测与线上排查。

## 模型实验室

回测从一次性命令行脚本变成了可按需调用的引擎（`server/lab.mjs`），
输出是**逐场记录**——五件事都只是在同一份输出上做不同切片，不必各写一遍重放。
历史数据压成 `data/backtest.json`（6150 场 484KB，brotli 后 46KB）随镜像走，
重放跑在工作线程里（一次约 60ms），结果按参数缓存。

**造一个模型** — 调 8 个参数，当场在 4920 场真实比赛上回测打分，
和默认模型、和「永远选主队」排在同一张榜上。你会撞上一些反直觉的事实：
关掉「赛季中学习」准确率从 66.1% 掉到 60.7%；而加大「上赛季净效率权重」
几乎没有任何影响。

**模型错在哪** — 把逐场记录按比赛类型切片。结论不是「有 bug」，而是难度分布：
实力接近的比赛 57.4%、实力悬殊的 81.6%，模型没把握时它确实也不该有把握。
真正值得警惕的是某一类比赛上持续的**分差偏置**——那是可以修的系统性误判。

**逐年测量** — 用数据回答真问题，而且直接改进了模型：

| 赛季 | 实测主场优势 |
| --- | --- |
| 2022-23 | 2.39 分 |
| 2023-24 | 2.15 分 |
| 2024-25 | **1.60 分** |
| 2025-26 | **1.62 分** |

主场优势在持续下降，而模型里写死的是 2.4——四年前的值。这导致最近两个赛季
分差偏置 +0.79（系统性高估主队），改成 1.6 后归零。
同样测出背靠背的真实代价是 −1.98 分而不是表里写的 −1.1，
`restWeight` 1.8 让整张表贴合实测（形状对、幅度估小了）。

诚实地说：这两处修正对胜负准确率几乎没有影响（噪声范围内），
真正被修好的是偏置——它对猜胜负无所谓，对预测比分和让分是实打实的错。

**反事实** — 「假如某队全季强 3 分，赛季会怎样」。测出每 1 分净胜分约合
**2.5 个胜场**，公认经验法则是 2.7，一个不错的交叉验证。
要注意这是「模型认为会怎样」而不是「历史真的会怎样」——改的是模型对球队的评级，
真实比赛结果无法反事实。

**对标盘口** — 把模型和 4908 场比赛的博彩收盘盘口逐场对账。
这一页刻意不做成爽点页：模型 66.3%、盘口 68.4%，McNemar 检验 χ²=15.70 说明差距是真的；
模型相对盘口选边的让分命中率 49.1%，低于 52.38% 的打平线。
真正有用的是「被拉开差距的地方」那张表——差距集中在背靠背和赛季末，
正好是轮换安排最不确定的时候。详见下方「对标博彩盘口」一节。

## 界面

「玻璃数据终端」风格：深色底铺当前球队主色的渐变光斑，内容层是半透明玻璃卡片，
卡片顶边一条队色辉光。进入某支球队页面时整站配色随之切换。

- **官方图片**：球队 logo 取自 `cdn.nba.com/logos/...`，球员头像取自 `cdn.nba.com/headshots/...`，
  加载失败时回退到队色缩写块 / 姓名首字母，离线也能用。
- **深 / 浅主题**：侧栏切换，选择记在 `localStorage`。
- **队色可读性校正**：篮网近乎纯黑、马刺是银灰，直接当强调色会在对应主题下糊掉，
  所以按亮度把过暗/过亮的队色拉回可读区间（`web/src/lib/color.js`）。
- 背景光斑用 `radial-gradient` 而不是 `filter: blur()`——视觉几乎一致，
  但省掉三个全屏尺寸的模糊图层。

`/style-preview.html` 保留了当初三个候选方案的对比页（队色沉浸式 / 体育杂志风 / 玻璃数据终端）。

**缺阵模拟**：在球队页或预测页勾选球员即可标记缺阵，该设置全站共享，会同步影响实力榜、
赛程胜率、单场预测和赛季模拟。

**伤病名单**来自 ESPN 公开接口（NBA 官方只发 PDF 伤病报告，没有结构化接口），
随每次 `npm run ingest` 刷新，带伤处、部位与预计复出日期。
名单里会显示「缺阵 / 每日观察」徽标，侧栏有一键套用「确定缺阵」的按钮。
ESPN 用自己的球员 id，靠归一化姓名匹配到 NBA 的 PLAYER_ID（去重音、去 Jr./III 后缀），
当前 75 条全部命中。

## 高阶数据与综合影响力指标

### 为什么没有 EPM / LEBRON / DARKO

这三个是当下最好的"all-in-one"球员影响力指标，但一个都接不进来，原因是两条硬约束：

| 数据源 | 这台机器能否访问 | 授权 |
| --- | --- | --- |
| dunksandthrees.com（EPM） | ✗ `http=000` | 部分收费 |
| bball-index.com（LEBRON） | ✓ 站点可达 | 免费数据在 Google 表格里 |
| docs.google.com | ✗ `http=000` | ← LEBRON 与 DARKO 的公开表格都在这儿 |
| github.com | ✗ `http=000` | RAPTOR 的开源数据（且 538 已停更，只到 2022-23） |
| stats.nba.com / ESPN | ✓ | 公开接口 |

即使能访问，EPM 与 LEBRON 也是收费产品，整份搬过来并不合适。

**但它们的输入我们全都有。** EPM 是拿 box score + 球场追踪 + on/off 回归出来的，
这三样 stats.nba.com 全部公开。所以这里的做法是自己训一个，
并且用这个项目一贯的标准去验证它。

### 每名球员 89 项数据

| 分组 | 项数 | 内容 |
| --- | --- | --- |
| 基础 | 21 | 得分、篮板、助攻、命中率、正负值… |
| 高阶 | 16 | PIE、使用率、真实命中、攻防效率、助攻率… |
| 官方估计效率 | 8 | `E_OFF/E_DEF/E_NET_RATING`——按球员贡献估计，不像 `OFF_RATING` 那样几乎等于在场时球队表现 |
| 拼抢 | 9 | 干扰投篮、抢断偏转、造进攻犯规、掩护助攻及其得分、卡位、争抢球 |
| 防守对位 | 5 | **被防投篮命中率 vs 对手正常命中率**——公开数据里最接近"个人防守好不好"的东西 |
| 球场追踪 | 24 | 突破、接球投篮、干拔、潜在助攻、助攻创造得分、触球与控球时间、篮板机会、跑动距离 |
| 得分构成 | 6 | 油漆区、快攻、二次进攻、失误转化、造犯规 |

球员页与球队页因此分成五个视图：基础 / 高阶 / 防守拼抢 / 得分方式 / 传球控球。

**比率类数据带样本门槛。** 对位出手不足 150 次时，对位压制（DIFF%）的标准差是
**13.68 个百分点**，超过 300 次只有 **3.04**——小样本噪声是 4.5 倍。不设门槛的话
榜首永远是只防过 5 次出手、DIFF% −43.7% 的边缘球员。所以对位类要求赛季 200 次对位出手、
突破/接球/干拔命中率要求 100 次出手；不达标的**照常显示数值但不参与排名**，
并标注样本量——隐藏行会让人以为数据缺失。

### EPM 是怎么算的（他们自己公开了）

不用逆向，[Dunks & Threes 的方法页](https://dunksandthrees.com/about/epm)写得很清楚，分两步：

1. **SPM**：把 box score、play-by-play、球场追踪数据回归到一个 18 年期的 RAPM
   （2001-02 ~ 2018-19）。统计量按**当时的**联盟平均标准化（"to account for the
   ever-evolving NBA game"），并考虑年龄对各项技术的不同影响。
2. **RAPM**：把上一步的 SPM 当**贝叶斯先验**，喂进一个按时间指数衰减的岭回归，
   用 2002 年以来的全部回合（22 个赛季、550 万个回合），**每名球员两个变量**
   （进攻、防守），控制主场优势与"橡皮筋效应"。每晚更新。

对照下来，我们缺的不是数据，是**第二步**，而且第一步的**回归目标也用错了**。

### IMP：自制的综合影响力指标

`server/impact.mjs` + `server/rapm.mjs`。含义与 EPM 一致：**相对联盟平均，
该球员每百回合给球队净效率贡献几分。**

```bash
npm run impact:fetch    # 5 个赛季的 box+追踪+on/off，约 8.5 分钟
npm run lineups:fetch   # 5 个赛季的五人组合数据，约 6 分钟
npm run impact:fit      # 算 APM、拟合 SPM、跨赛季验证、写出 data/impact-model.json
npm run ingest          # 把指标贴到每名球员上
```

#### 构成：一半统计栏，一半场上实测

```
IMP = 0.35 × 衰减 APM(近 3 季)  +  0.65 × SPM(box + 追踪)
```

两半各自不完整：SPM 只看统计栏，看不见球员真实带来的胜负；APM 只看场上结果，
样本噪声大且分不开总在一起打的人。EPM 的做法是把 SPM 当贝叶斯先验喂进 RAPM，
我们用固定权重线性混合，方向一致、实现简单得多。

**APM 怎么来**：`leaguedashlineups` 给每个五人组合的回合数与攻防效率
（每赛季约 256,000 个回合）。把每个组合当一条观测、球员当 0/1 自变量、
回合数当权重做岭回归，进攻防守分开拟合——与 EPM 的 "two variables per player" 一致。
再把近 3 季按半衰期 1 季做时间衰减合并。

#### 验收标准换过一次，这一步比调参重要

原来用「同赛季 APM」，有两个毛病：

1. **循环**：IMP 里含当季 APM，等于拿目标的一部分去预测目标
2. **不对题**：这个应用本来就是拿上赛季数据预测下赛季

改成 **「用第 N 季的数据预测第 N+1 季的真实表现」** 之后，所有数字才可信可比。
下面所有结果都用这个标准，SPM 训练时看不到第 N 季。

#### 三个负面结果，都留档

**年龄项没用。** EPM 明说用了年龄，我们加上年龄与年龄平方后 r 从 0.4571 变 0.4573，
完全在噪声里。EPM 有 22 个赛季撑得起年龄曲线，我们只有 5 季。代码留着，默认不启用。

**照搬 EPM 的第二步反而更差。** 试过把 SPM 当先验内嵌进 APM 的岭回归

**不如简单混合的 0.4061**。忠实照搬未必更好——EPM 有 550 万个回合和对手阵容撑着。

**裸 on/off 当训练目标是错的。** 最早用它，前十里混进 Paul Reed、Thybulle、

（第 N 季预测第 N+1 季同一指标）：APM **0.398** / on/off **0.286**，四对赛季全胜。

#### 解析 play-by-play 做真 RAPM：做完了，没用上

之前这里写着「最大的已知缺陷是没有对手调整，要修得解析每场的 play-by-play」。
那件事做完了，结论是**修得了缺陷，但换不来更好的指标**。全过程留档，
因为一个做扎实了的负面结论和正面结论一样值钱。

**做了什么。** 抓了 5 个赛季共 6150 场的逐条 play-by-play，还原每一段场上的十个人，
得到 182,543 段带攻守双方阵容的观测（`server/pbp.mjs` + `scripts/pbp-history.mjs`）。
接口有三个坑：`playbyplayv2` 已经空返回；v3 的换人事件只给**下场**球员的 id，
上场的人只有描述里一个姓氏（所以每场还得配一次 box score）；**节间换人不记事件**，
每节的开场五人必须单独推断。同队重名会写成 "K. Martin"，变音符会写成 "Matkovic"。

**怎么确认还原是对的。** 两条独立的验证，不是靠读代码：

1. 逐人对账：还原出的出场时间与 box score 的分钟数比，对不上整场丢弃。
   五季平均 **97.2%** 的比赛通过（丢弃 174 场）。
2. 回归自己解出来的**主场优势**——我们从没把主场信息喂给它：

| 赛季 | 2021-22 | 2022-23 | 2023-24 | 2024-25 | 2025-26 |
| --- | --- | --- | --- | --- | --- |
| RAPM 解出的主场项 | 1.73 | 2.18 | 2.00 | 1.50 | **1.41** |
| 模型里逐场实测校准的主场优势 | — | 2.39 | — | 1.60 | 1.62 |

两条线是各自独立算出来的（一条来自 18 万段阵容回归，一条来自逐场分差拟合），
量级和「持续下降」这个趋势都对得上。这是阵容还原正确的最强佐证。

**对手调整确实起作用了。** 球员评分与所在队净效率的相关，
从 APM 的 **0.589** 降到 RAPM 的 **0.425**（2025-26）。好球员本来就在好队，
这个相关不该归零；降下来的这部分就是「队友好 ⇒ 对手也被队友压住 ⇒ 两份好处
全算你头上」的污染。被压得最狠的正是强队的板凳角色球员。

**但它换不来更好的预测。** 主判据仍是那把独立的尺子——预测次季裸 on/off：

| 3 季衰减，只看实测那一半 | 次季 on/off | 次季 APM | 次季 RAPM |
| --- | --- | --- | --- |
| 衰减 **APM**（现用） | **0.301** | **0.429** | 0.404 |
| 衰减 RAPM | 0.297 | 0.420 | **0.413** |
| 纯 SPM | 0.327 | 0.412 | 0.410 |

RAPM **只在「预测次季 RAPM」上赢**——只更擅长预测它自己，那正是共享偏差的定义。

混合之后，三方权重扫了一整个网格，**最优解把 RAPM 的权重压到 0**：

| wA \ wR | 0.00 | 0.10 | 0.15 | 0.20 | 0.30 |
| --- | --- | --- | --- | --- | --- |
| 0.20 | 0.3485 | 0.3495 | 0.3485 | 0.3466 | 0.3410 |
| 0.25 | 0.3502 | 0.3491 | 0.3473 | 0.3448 | 0.3382 |
| **0.30** | **0.3507** | 0.3478 | 0.3453 | 0.3422 | 0.3349 |

曲面很平，所以不是 RAPM 有害，是它**冗余**：和 APM 携带同一份信息，只是方差更大。
EPM 的原方法（把 SPM 当先验内嵌进岭回归，而不是固定权重线性混合）也试了，
最好 0.3387，仍不如线性混合的 0.3507——**这是第二次输给我们的简化版**。

**但这个差不显著，必须说清楚。** 配对比较（同一批球员、同一个赛季对）：

| w=0.30 赛季对 | IMP(APM) | IMP(RAPM) | 配对差 |
| --- | --- | --- | --- |
| 21-22→22-23 | 0.3818 | 0.3775 | +0.0043 |
| 22-23→23-24 | 0.3450 | 0.3290 | **+0.0160** |
| 23-24→24-25 | 0.3242 | 0.3260 | **−0.0018** |
| 24-25→25-26 | 0.3516 | 0.3483 | +0.0034 |
| **平均差** | | | **+0.0055** |

标准误 0.0038，**t = 1.45（自由度 3）**，离 p<0.05 需要的 3.18 差很远。
平均差的一多半来自单独一个赛季对，去掉它剩下三对只差 +0.0020，而且 4 对里
RAPM 赢了 1 对。**所以正确的说法是「打平」，不是「APM 赢」。**

**为什么。** 对手调整让自由参数翻倍，每人的防守系数要靠对手方的观测去定，
而我们每季只有约 24 万回合。EPM 有 **550 万回合、22 个赛季**。
和年龄项那次是同一个道理：方法本身没问题，是数据量撑不住。

**代价与收益，摆出来看。** 换成 RAPM 之后，之前点名过的那几个被抬高的角色球员：

| | IMP(APM) | IMP(RAPM) |
| --- | --- | --- |
| Paul Reed（队净效率 +8.4） | 2.20 **#8** | 2.21 **#11** |
| Matisse Thybulle | 1.98 **#11** | 1.82 **#17** |
| Ajay Mitchell（队净效率 +11.1） | 1.96 **#12** | 1.76 **#19** |

榜单确实更合理了（文班 #3→#2、伦纳德 #5→#4、东契奇 #9→#7），但幅度小
（Paul Reed 还是第 11），因为混合里实测只占 35%。

**决定是保持 APM，依据是「拿不出改进的证据就不引入成本」**——多一条管线、
17MB 数据、每次刷新当季要重抓约 3 小时，而准确率上测不出差别。
**这不等于 RAPM 被证伪了。** 既然是平局，「消除一个已知偏差」本身就是一条
站得住的支持理由；想换过去是完全合理的判断，只是当前没有数据强迫我们换。

#### 关于「年度稳定性」这把尺子的一个修正

上一版里我用年度稳定性（第 N 季的值预测第 N+1 季**同一指标**）作为
「裸 on/off 不该当训练目标」的依据。这次 RAPM 的正则扫描暴露了它的漏洞：

| RAPM 正则强度 λ | 年度稳定性 | 预测次季 on/off |
| --- | --- | --- |
| 2000 | 0.368 | **0.271** |
| 6000 | 0.423 | **0.271** |
| 20000 | 0.468 | 0.252 |
| 60000 | **0.483** | 0.236 |

**两条判据方向完全相反。** 正则越强，所有人越被收缩到 0，年度间自然越稳定，
同时也越没信息量——稳定性可以被「什么都不说」刷出来。

所以年度稳定性只能当**体检项**（噪声大的指标必然低），不能当**验收标准**。
原来那个 APM 0.398 对 on/off 0.286 的结论是在两个不同指标之间比的，
不像同一指标调参那么容易被刷，方向大概率仍然对；但它不该是唯一依据。
本节和上面所有的验收结论都改用了独立的那把尺子。

#### 三个必须说清楚的局限

**一、系数不能当因果读。** 15 个特征彼此高度相关，岭回归为了预测准会把权重
在相关特征之间任意分配。所以模型里"得分""潜在助攻""掩护创造得分"的系数是**负的**，
"干扰投篮"接近 0——这不代表这些事没用，只代表它们的信息已经被别的特征吸收了。
整体预测有效，单个系数不可解释。

**二、不在训练区间内就不给分。** 模型只在「出场 ≥20 场、场均 ≥10 分钟」的球员上
训练过。第一版没设这个限制，一个打了 1 场 2.7 分钟的球员拿到 **−42.67**——
那不是评价，是线性外推的产物。现在门槛外一律返回空值，680 名球员里 406 人有 IMP。

**三、没有对手调整。** 这是与 EPM 最实质的差距，也是当前最大的已知缺陷：
实测那一半（APM）只看得到进攻方五人，所以**总在一起上场的球员分不太开**——
强队的角色球员会被抬高，榜单上还能看到这个痕迹（Paul Reed 第 8、Ajay Mitchell 第 12）。

**这条不再是猜测了。** 我们解析了 5 季 6150 场的 play-by-play，做出了带对手调整的
真 RAPM，量出污染确实存在（球员评分与所在队净效率的相关 0.589 → 0.425）。
但换上去之后预测能力**测不出改善**（配对 t=1.45，不显著），所以没有为它增加
一条 17MB + 3 小时抓取的管线。详见 [docs/rapm-verdict.md](docs/rapm-verdict.md)。

也就是说：这个缺陷是真的，我们知道它有多大，也知道以现有数据量**修了也看不出好处**——
要真正修好它需要的不是更好的方法，是 EPM 那样的 550 万回合。

#### 一次彻底失败的尝试，留档

最早的版本在**球队层面**拟合系数（球队分钟加权特征均值 → 球队净效率），再套回个人。
结果 Mitchell Robinson 拿到 **+341.60 分/百回合**，前十二名全是蓝领中锋，
留一 R² 只有 0.843——**还不如只用 PIE 的 0.880**。

两个错叠在一起：球队平均值的方差比个人小一个量级，个人偏离除以球队标准差会放大二十倍；
而且球队层面根本分不开个人贡献，模型只学到了"内线多的队净效率高"。

## 预测模型

球队实力统一折算成「相对联盟平均的每场净胜分」：

```
实力 = (Elo折算分 × wElo + 净效率折算分 × wNet) / (wElo + wNet) + 阵容更迭 + 缺阵修正
分差 = 主队实力 − 客队实力 + 主场优势 + 休息修正
胜率 = Φ(分差 / 分差标准差)
```

**Elo** — 采用 [FiveThirtyEight 公开的 NBA Elo 方法](https://fivethirtyeight.com/features/how-we-calculate-nba-elo-ratings/)：
K=20，分差放大项 `((mov+3)^0.8) / (7.5 + 0.006 × 胜方Elo差)`，主场优势 100 Elo，
赛季间按 `0.75 × Elo + 0.25 × 1500` 向均值回归。中立场不给主场优势。
**赛季开打后继续吸收本赛季已完成比赛** —— 这是准确率的主要来源，见下方回测。

**净效率** — 上赛季百回合净效率 × 节奏 / 100，折算成每场分差。

**轮换影响力** — 阵容相关计算的统一基础：按**整季总出场分钟**（场均 × 出场数）降序取球员，
累计到球队整季总分钟（240 × 82）为止，累加 `(PIE − 0.085) × 分钟`，再除以 82 折算成每场。

> 必须用总分钟而不是场均分钟：垃圾时间被临时召上来的球员场均分钟可以很高
> （某队有人 6 场打了 36.2 分钟），按场均排序会把他们顶到轮换首位。

用 30 队的「上赛季名单 → 上赛季净效率」做最小二乘，得到把影响力换算成每百回合得分的系数，
**R² = 0.89**。

**阵容更迭** — 新赛季名单与上赛季名单轮换影响力之差，联盟层面做零和归一
（净效率的联盟平均恒为 0，个别球员退役不该抬高整体水位）。
**默认强度只有 0.15，因为回测证明这一项拿不出可验证的增益**，详见下方回测一节。

**缺阵修正** — 把勾选的球员移出轮换后重算影响力，空出的时间由名单里排在后面的人顶上。
下限为 0：替补顶上最差也就是持平，缺人不会让球队变强。

**假设全员健康**（侧栏开关）— 新赛季名单的分钟口径。默认沿用上赛季实际出勤，
但这会埋没上赛季伤停的球星：塔图姆只打了 16 场、字母哥 36 场、恩比德 38 场、库里 43 场，
全联盟有 14 名 PIE ≥ 0.13 的主力属于这种情况。开启后改用 `场均分钟 × 70 场` 估算，
只对上赛季出场满 10 场的球员生效——否则垃圾时间打几场高分钟的临时工会被误当成主力。
两种口径都不改动上赛季基准（它必须解释上赛季的真实净效率），
所以是两个可对照的情景，而不是一个藏起来的启发式规则。

> 实例：默认口径下凯尔特人排第 15、预计 41.4 胜；开启后升到第 6、48.5 胜。

**休息修正** — 背靠背 −1.1 分，休 2 天 +0.35 分，休 3 天及以上 +0.5 分。

**比分** — 由双方进攻/防守效率对位（`己方进攻 + 对手防守 − 联盟平均`）与节奏推出总分，
再按预期分差拆分成两队得分。

**赛季模拟** — 每次模拟先给每队抽一个标准差 2 分的实力扰动（代表赛季前评估本身的误差），
再逐场按胜率抽样。默认 3000 次。

模型参数（主场优势、Elo/净效率权重、休息强度、缺阵强度、阵容更迭强度、分差标准差、
是否假设全员健康）都可以在「比赛预测 → 模型参数」里实时调整，调整后全站生效。

## 回测：模型到底准不准

### 阵容与预计分钟实验（独立于线上排名）

新增离线实验，检验休赛期人员变动能否改善滚动 Elo。按当前名单的预计分钟
（全队 240 分钟）加权球员影响力，与历史 Elo 混合初始化，再逐场吸收赛果。
混合权重仅在较早赛季选择，后续赛季作为留出集；同时对比纯 Elo 和原阵容修正。
报告全季、任一球队未打满 10 场、以及高人员流失球队的概率与分差误差。

```sh
npm test
npm run backtest:roster -- --input tests/fixtures/roster-experiment/synthetic.json
npm run backtest:roster -- --audit
```

示例为虚构数据，只验证计算与防止未来数据泄漏的逻辑，**不证明 NBA 预测能力**。
真实回测需要每季开赛前已经可得的名单、预计分钟、伤病与球员评级快照，不能拿
全季名单或未来实际分钟替代。审计缺少数据时返回退出码 2，不联网补造预测。
输入格式见 [实验数据说明](docs/roster-experiment-inputs.md)，
执行结论见 [实验记录](docs/roster-experiment-verdict.md)。线上默认值暂不改变。

`npm run backtest` 在历史赛季上逐场重放预测。做法是对每个被测赛季只用开赛前
能拿到的信息建立初始评级，然后按日期顺序逐场预测——预测记录完成后才用真实
结果更新评级，不存在信息泄漏。

2022-23 ~ 2025-26 共 **4920 场**：

| 模型变体 | 胜负准确率 | Brier | LogLoss | 分差 MAE |
| --- | --- | --- | --- | --- |
| 评级冻结在赛季前（旧版行为） | 61.38% | 0.2351 | 0.6642 | 11.67 |
| ＋赛季中滚动更新 Elo | 64.19% | 0.2199 | 0.6300 | 11.14 |
| **＋滚动更新，纯 Elo（当前默认）** | **66.32%** | **0.2136** | **0.6154** | **10.91** |
| 基准线：永远选主队 | 55.59% | 0.4440 | — | — |

分阶段看，旧版模型随赛季推进不断退化，而滚动更新版一路走高：

| | 赛季初 (<10场) | 赛季中 (10-40场) | 赛季末 (≥40场) |
| --- | --- | --- | --- |
| 评级冻结 | 64.21% | 62.32% | 59.98% |
| 滚动更新纯 Elo | 65.33% | 65.40% | 67.24% |

隔离对照说明**这 5 个百分点全部来自"赛季中学习"，与权重配比无关**：
在评级冻结的前提下，纯 Elo (61.42%)、Elo+净效率混合 (61.38%)、纯净效率 (61.10%)
三者几乎没有差别。所以默认权重改成了纯 Elo，净效率滑块保留但默认为 0。

### 阵容更迭修正：一个被回测否掉的功能

把阵容更迭项也纳入回测后，结论是**它无法证明有价值，而原来的默认强度是有害的**：

| 阵容更迭强度 | 胜负准确率 | Brier |
| --- | --- | --- |
| 0（不启用） | **66.32%** | 0.2136 |
| 0.15（当前默认） | 66.16% | **0.2133** |
| 0.27（理论最优） | 65.96% | 0.2141 |
| 0.4 | 65.61% | 0.2160 |
| 0.8（曾经的默认） | 63.86% | 0.2262 |

诊断（30 队 × 4 赛季 = 120 个样本）：

- 更迭预测值与球队实际净效率变化的相关系数 **r = 0.229** —— 方向是对的，
  但只解释约 5% 的方差。
- 预测值标准差 4.19 分/场，实际变化标准差约 5.0。按最优线性预测，
  权重应该是 `r × σ实际/σ预测 ≈ 0.27`，而应用原本用的是 **0.8，超了约 3 倍**。
- 系统性偏差：名单里「上赛季无 NBA 数据」的球员平均占 19.5%，
  它与更迭预测值的相关系数是 **−0.213** —— 新秀多的重建队被系统性判为变弱。
  这是信号被稀释的主要原因之一，要修需要引入选秀顺位先验。

所以默认强度从 0.8 降到 0.15（该权重下 Brier 最优，但相对不启用的增益仍在噪声内）。
界面上的「阵容更迭」列继续展示，滑块可调，但**不要把它当成已验证的准确率来源**。

#### 后来把球员价值从 PIE 换成了 IMP

上面那张表里的「阵容更迭」用 PIE 衡量球员价值。有人问了个好问题：
湖人用 41 岁的勒布朗换来一批有防守的年轻人，模型为什么判成变弱？

查下来 PIE 确实撑不住这个判断——它是纯统计栏指标，看不见防守，也没有年龄项。
按 PIE，勒布朗上赛季对湖人的边际价值是 **−6.05 分/场、全联盟第 17**；
而含追踪数据与场上实测的 IMP 只给他 **0.71**，也就是一个普通轮换。
按分钟加权，离队那批人的 IMP 是 0.18，加盟那批是 **0.28**——进来的人并不差，
差的是分钟总量（走了 11,717 分钟，只进来 8,692）。

换成 IMP 之后，先看不打折的判据：**用第 N 季的球员数值 + 第 N+1 季的名单，
预测第 N+1 季的球队净效率**。

| 球员价值口径 | 跨季相关 r | 同季拟合 R² |
| --- | --- | --- |
| PIE（旧） | 0.612 | 0.890 |
| **IMP（新）** | **0.653** | **0.950** |

替补级基准扫过一遍：IMP 取 −4 时跨季相关能到 0.694，比采用的 −0.5（0.653）更高。
**没有采纳。** 替补级压得越低，这一项就越接近「名单总分钟」——而光数名单总分钟、
完全不看球员好坏，本身就有 **r = 0.49**。那是「上赛季谁健康打得多」的信号，
是真的，但不该伪装成一个衡量球员质量的项混进来。采用的 −0.5 有两个独立锚点：
实测每队第 10 人起的分钟加权 IMP 是 −0.65；把旧的 PIE 0.085 换算过来是 −0.49。

回测（4920 场）——**必须说清楚，逐场层面的差别基本在噪声里**：

| 变体 | 胜负准确率 | LogLoss | 赛季初 n=623 |
| --- | --- | --- | --- |
| 不启用（基线） | 66.32% | 0.6154 | 65.33% |
| PIE w=0.15 | 66.16% | 0.6150 | **63.88%** |
| **IMP w=0.15（当前）** | 66.24% | **0.6148** | 65.01% |
| PIE w=0.4 | 65.61% | 0.6215 | 64.04% |
| IMP w=0.4 | **66.34%** | 0.6155 | 65.17% |

4920 场的准确率标准误约 ±0.7 个百分点，所以 66.16 → 66.24 什么都证明不了。
真正能看出来的是两处：

1. **赛季初**（阵容更迭本该最有用的地方）PIE 是倒扣 **1.45 个百分点**的，IMP 把这个损害基本消掉
2. **权重加大时 PIE 会崩、IMP 不会**：w=0.4 时 PIE 掉到 65.61%（比不启用还差 0.7pp），IMP 仍有 66.34%

结论保持不变：**这一项依然无法证明比不启用更好**，只是换成 IMP 之后不再有害。
默认强度仍是 0.15。

口径由 `meta.rotationBasis` 记录，`buildModel` 以它为准。这不是洁癖：
`teams.json` 里的 `rotationPrior` 是 ingest 按某个口径算好写进去的，
运行时要是自作主张换一个，就会拿 IMP 量纲的新名单去减 PIE 量纲的旧基准——
实测湖人的阵容更迭会算成 **+206 分/场**。

需要说明的是，这个测试对该功能是偏宽容的：历史赛季的名单接口返回该赛季全程名单，
含交易截止日才加盟的球员，用来预测赛季初的比赛存在轻微信息泄漏。
连这个乐观上界都测不出增益。

回测数据缓存在 `data/history/`，重跑不会重复抓取。

## 对标博彩盘口

模型准不准，最有说服力的标尺不是「永远选主队」，而是**博彩市场**——它是公开可得
的最强对手之一，价格里已经含进了轮换安排、临场伤情和球队动机。

### 盘口从哪来（不需要 api key，也不需要爬虫）

ESPN 自己的公开接口就带盘口，数据来自持牌博彩公司。两个端点分工不同，
这是实测出来的：

| 端点 | 用途 | 关键限制 |
| --- | --- | --- |
| `site.api.espn.com/.../scoreboard?dates=YYYYMMDD` | 当天全部比赛的 eventId、两队、比分、**未开赛比赛的盘口** | 已结束的比赛 `odds` 字段是空的 |
| `sports.core.api.espn.com/.../events/<id>/competitions/<id>/odds` | 单场盘口，**历史比赛也有**，带 open/close/current | 一场一个请求 |

第二个端点单场 6.8KB；同样内容走 `summary` 端点要 397KB，**58 倍差距**——
抓 5000 场时这个差别决定了这件事可不可行。

```bash
npm run odds:history   # 抓 4 个赛季的收盘盘口 → data/history/odds_*.json，约 2 分钟
npm run dataset        # 把盘口并进 data/backtest.json（不重新抓 NBA 数据）
npm run ingest         # 日常抓取，顺带刷新未开赛比赛的实时盘口 → data/odds.json
```

`odds-history` 可中断可续跑，每 50 场落一次盘，重跑跳过已有的比赛。
实际覆盖 **4908/4910 场（99.96%）**。

诚实说明：ESPN 各年份的默认博彩商不同（2022-23/2023-24 是 Betfair，
2024-25 起 ESPN BET，当前 DraftKings），不同博彩商的让分通常差 0.5 以内。
我们把 provider 一起记下来，不假装是同一个源。

### 结果：市场更准，而且差距是显著的

4908 场有收盘盘口的比赛上：

| | 胜负命中率 | Brier | LogLoss | 分差 MAE | 分差偏置 |
| --- | --- | --- | --- | --- | --- |
| 我们的模型 | 66.26% | 0.2129 | 0.6139 | 10.90 | −0.31 |
| **博彩盘口** | **68.40%** | **0.2015** | **0.5873** | **10.42** | **−0.00** |

比较用的是同一批比赛、同一把尺子：市场胜率取两边钱线**去掉抽水**后的值，
缺钱线时才退回用同一个 `spreadSd` 把让分折成概率。

差 2.1 个百分点听起来不多，但两边共享绝大多数容易的比赛，直接比命中率会低估差距。
McNemar 检验只看两边判断不同的 689 场：模型独对 292 场，盘口独对 397 场，
χ² = 15.70，**p < 0.001，差距是真的**。

逐年看，差距在收窄：

| 赛季 | 模型 | 盘口 | 差距 |
| --- | --- | --- | --- |
| 2022-23 | 62.68% | 65.69% | −3.0 pp |
| 2023-24 | 65.85% | 69.43% | −3.6 pp |
| 2024-25 | 67.32% | 69.20% | −1.9 pp（不显著） |
| 2025-26 | 69.20% | 69.28% | −0.1 pp（不显著） |

2025-26 模型独对 83 场、盘口独对 84 场，基本打平。但这是**单季 1224 场**的结果，
不足以说明模型已经追上——趋势值得记着，不值得当结论。

### 让分盘：没有可利用的优势

这是唯一能变成「下注建议」的部分，结论是否定的：

| 模型与盘口的分歧 | 场次 | 让分命中率 | 相对打平线 |
| --- | --- | --- | --- |
| 0 ~ 1 分 | 1056 | 50.9% | −1.5 pp |
| 1 ~ 2 分 | 1009 | 48.4% | −4.0 pp |
| 2 ~ 3 分 | 832 | 45.2% | −7.2 pp |
| 3 ~ 5 分 | 1209 | 50.7% | −1.7 pp |
| 5 分以上 | 802 | 49.4% | −2.9 pp |
| **合计** | **4908** | **49.12%**（±1.41） | **−3.3 pp** |

-110 抽水下打平需要 **52.38%**。整体 49.12%，每一档都在打平线之下，
而且**分歧越大命中率并没有越高**——这正是「没有优势」的样子，
而不是「优势藏在某一档里」。

所以盘口在这个项目里的定位是：**标尺，不是提款机**。
界面上会显示模型与盘口的分歧，但同时写明它不构成下注建议。

### 盘口不参与模型计算

这是个刻意的选择。一旦让盘口进模型，「和市场比谁更准」就没有意义了，
而且模型会退化成盘口的复读机。所以 `predictGame` 完全不知道盘口的存在，
盘口只在 API 响应里以 `market` 字段挂在预测**旁边**。

### 差距在哪，就该改哪

| 比赛类型 | 场次 | 模型 | 盘口 | 命中率差 |
| --- | --- | --- | --- | --- |
| 背靠背相关 | 1460 | 66.92% | 70.34% | **−3.4 pp** |
| 赛季末 (≥60场) | 1287 | 69.93% | 72.80% | **−2.9 pp** |
| 实力接近 (Elo 差<50) | 1311 | 57.82% | 60.34% | −2.5 pp |
| 赛季初 (<10场) | 621 | 63.93% | 66.02% | −2.1 pp |
| 实力悬殊 (Elo 差>200) | 1031 | 81.57% | 81.77% | −0.2 pp |

实力悬殊的比赛我们和市场几乎一样准——那种比赛谁都会做。
差距集中在**背靠背**和**赛季末**：这两类恰恰是轮换安排最不确定的时候，
盘口能看到「今晚谁不打」，我们看不到。差距的大小，就是这个信息值多少分。

## 已知局限

- **新秀与海外新援按替补级计算。** 他们出现在名单里，但上赛季没有 NBA 出场记录，
  总分钟为 0，既不占轮换时间也不贡献实力。对手握高顺位新秀的重建队，模型会偏保守。
- **上赛季伤停的球星在默认口径下被低估**，用侧栏的「假设全员健康」切换情景；
  该开关无法区分"伤愈复出"与"确实会继续缺阵"，只是给出乐观一侧的边界。
- **PIE 低估无球防守与组织牵扯。** 防守型球员的价值会被算低，个别首发的「缺阵影响」
  甚至显示 ≈0（PIE 低于替补级基准）。
- **球星缺阵损失落在 8~12 分区间**，与博彩市场对 MVP 级球员的盘口变动大体一致，
  但 PIE 无法区分「高出场量」和「高价值」，出场时间极多的非超巨会被高估。
  可以调低「缺阵影响强度」。
- 赛季中被交易的球员，其整季分钟全部计入最后效力的球队。
- 赛季模拟的分区排名用随机数打破平局，未实现 NBA 官方的相互战绩等平局规则。
- 阵容更迭修正已纳入回测并被否掉（见上），默认强度降到 0.15。
- **缺阵修正仍未被验证**：回测需要逐日的历史伤病名单，ESPN 接口只给当前状态、
  不提供回溯查询，因此这一项的增益无法量化。它的量级不小（约基奇缺阵 −11.9 分），
  是模型里最大的未知数，使用时请自行判断。
- 伤病数据是抓取时的快照，不是实时的。赛季中要保持准确需要重新跑 `npm run ingest`。
- **盘口是增强项，可能缺失。** ESPN 这个接口没有公开文档也没有 SLA，字段随时可能变；
  博彩商通常只提前几天到几周挂线，所以远期比赛拿不到盘口是正常的。
  拿不到就退回纯模型，页面不会因此挂掉。
- 休赛期抓到的多是赛季前手术记录（带较远的预计复出日期），赛季开打后才会反映真实出勤。
- NBA 杯淘汰赛（6 场）为待定对阵，不参与模拟；因此每队排定场次为 80 场而非 82 场。

## API

| 接口 | 说明 |
| --- | --- |
| `GET /api/meta` | 赛季信息、默认参数、数据量 |
| `GET /api/teams` · `GET /api/teams/:id` | 球队列表 / 球队详情（含阵容、转入转出、带预测的赛程） |
| `GET /api/players?teamId=&onRoster=1` | 球员数据，附 `outCostPts`（缺阵影响）与 `injury`（伤病状态） |
| `GET /api/injuries` | ESPN 伤病名单快照 |
| `GET /api/schedule?type=&teamId=&from=&to=&limit=` | 赛程（默认带预测，`predict=0` 关闭） |
| `GET /api/rankings` | 旧 Elo 实力榜；`rankingModel=roster` 返回实验阵容排名 |
| `POST /api/predict` | 单场预测 `{homeId, awayId, gameId?, neutral?, out?, params?}` |
| `POST /api/simulate` | 赛季模拟 `{sims?, out?, params?, seed?}` |
| `POST /api/lab/market` | 模型 vs 博彩收盘盘口的对账结果 |
| `POST /api/refresh` | 重新抓取数据并热加载（生产环境用 `ALLOW_REFRESH=0` 关闭） |
| `GET /api/health` | 线程池 / 缓存 / 内存 / 数据库状态 |
| `POST /api/players` | 创建玩家，返回一次性令牌 |
| `GET /api/me` · `POST /api/me/name` | 用令牌确认身份 / 改名 |
| `POST /api/picks` | 同步预测，得分由服务端计算 |
| `GET /api/leaderboard?mode=&min=` | 排行榜（10 秒缓存） |

GET 接口可用 `?out={"teamId":[playerId]}`（JSON 字符串）传入缺阵名单，
以及 `?homeAdv=3&wElo=0.6&turnoverWeight=0&assumeHealthy=1` 等参数覆盖。

本地总览默认展示「阵容 + 战绩（实验）」= 阵容先验 + 本季战绩修正：r = (K·阵容先验 + Σw·对手调整净胜分)/(K+Σw)，K=12，每场权重 w = 0.4^(距今天数/60)（留一赛季回测选出，
`npm run roster:results`，结论见 `docs/roster-results-update-verdict.md`）；对手调整取同一张榜的强度迭代求解，主场优势 1.6 分、中立场不计。
阵容先验只取现役名单，按「出场时预计分钟 × 轮换概率 × 伤病出场概率」分配全队 240 分钟（单人期望上限 38，见 `docs/roster-fixes-batch1-verdict.md`），
再汇总球员 IMP，减去同一伤病口径下的联盟均值；某队算不出来只影响该队。本季 IMP 按 K=38 场收缩。
缺失 IMP 的球员用统计栏 SPM 估计（新秀先验 −0.67），标为「未验证」；常数由 `node scripts/roster-shrinkage.mjs` 拟合。表中显示覆盖率；点击球队可核对分钟和贡献。
`rankingModel=roster&availability=reported` 计入快照中确定缺阵球员，`availability=healthy` 忽略已报伤病；两种模式均保留手动缺阵。
可切换「旧 Elo 对照」，比赛预测与模拟仍使用原模型。回测（先验用上述新分钟口径）中新榜比只看阵容显著更准（留一赛季 log loss −0.027），比旧 Elo 低 0.006（留一赛季区间不含 0，最终留出季 −0.004 区间含 0），优势很小。

## 数据更新

新赛季开打后重新抓取即可自动切换基准赛季：

```bash
npm run ingest
# 或指定赛季
PRIOR_SEASON=2026-27 TARGET_SEASON=2027-28 npm run ingest
```

赛季中的日常刷新（含实时盘口）：

```bash
npm run ingest        # 球队/球员/赛程/伤病 + 未开赛比赛的盘口
```

历史盘口只需抓一次——收盘之后就不会再变：

```bash
npm run odds:history  # → data/history/odds_*.json，可中断续跑
npm run dataset       # 并进 data/backtest.json
```

> **部署说明：每天定时重建（2026-10-27 起）。** Docker 镜像把 `data/` 烤进镜像（见 Dockerfile 顶部注释），
> 所以线上数据只和最后一次构建时一样新。
>
> **这一条改过决定。** 原来刻意不加定时重建的 cron，理由是「数据烤进镜像、运行时零外呼」——
> 定时重建等于让服务器按点去抓 NBA 和 ESPN。休赛期这个取舍是对的：没有新比赛，快照不会过时。
> 2026-27 赛季开打后代价变了：每天约 7 场新结果不进 Elo，伤病与盘口几天就过期，
> 而 Elo 的赛季中滚动更新恰恰是准确率的主要来源（61.4% → 66.3%，见「回测」）。
> 高磊 2026-10-27 选择改为每天自动刷新。
>
> 原则没有全丢：**运行中的应用仍然零外呼**（`/api/refresh` 照旧关闭），
> 外呼只发生在 `deploy/refresh.sh` 的抓取阶段，在临时目录里进行，
> 体检不过或新容器不健康都不会换掉线上快照。安装与回滚见 [deploy/README.md](deploy/README.md)。
>
> **更新（同日）：第一条风险成真了。** 服务器和海外机房的 IP 都被 NBA 封了，只有宽带能抓。
> 现在的做法是服务器每天用 ESPN 补比分/Elo/伤病/盘口，全量统计由本机推送，
> 架构与验证见 [deploy/README.md](deploy/README.md)「自动刷新是怎么搭起来的」。
>
> **这个决定最可能错在哪：** 一是服务器 IP 可能根本连不上 stats.nba.com（很多云主机被拒），
> 那样 cron 会每天静默失败、线上停在旧数据——所以安装第一步是 `--fetch-only` 实测；
> 二是每天固定时间抓取可能触发限流（被封时是挂起不是 429），脚本有 30 分钟超时和 `flock`，
> 但连续失败不会通知任何人，判断它是否在跑要看 `/api/meta` 的 `fetchedAt`。
>
> 与此配套，界面上会显示盘口的抓取时间；超过 3 天会显式提示可能已改线——
> 自动刷新坏掉时，这条提示就是线上能看到的信号。

数据来源为 NBA 官方 stats.nba.com 与 ESPN 公开接口，仅供个人学习研究使用。

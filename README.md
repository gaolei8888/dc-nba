# NBA超级幻想

一个本地运行的 NBA 数据与比赛预测应用：涵盖 30 支球队的基础/高阶数据、全联盟球员数据、
2026-27 赛季完整官方赛程，以及基于 Elo + 效率评级 + 阵容影响力的比赛预测与赛季蒙特卡洛模拟。

## 快速开始

```bash
npm install
npm run ingest      # 从 stats.nba.com 抓取数据，约 45 秒
npm run backtest    # 在历史赛季上回测模型准确率（首次会抓 5 个赛季）
npm run check       # 检查 JSX 里的组件引用（build 会自动跑）
npm start           # 构建前端并启动服务 → http://localhost:5174
```

开发模式（前端热更新）：

```bash
npm run dev         # 前端 http://localhost:5173，API 5174
```

## 人机对赌

对已结束赛季的真实比赛做预测，跟模型比谁更准。

**模型的对手盘是无信息泄漏的。** `server/replay.mjs` 逐日重放上赛季：走到某场比赛时，
先记录模型的预测，再用真实结果更新 Elo。所以模型在每场比赛前掌握的信息和你一样多，
不存在"事后诸葛亮"。生成的题库落在 `data/gameday.json`（1230 场，含模型赛前判断与真实比分）。

**计分**：猜对得 `(信心 − 50%) × 200` 分，猜错扣同样的分。信心 55% 猜对得 10 分，
95% 猜对得 90 分、猜错扣 90 分。这样设计是为了让"下重注"只有在判断确实优于抛硬币时才划算。
另外同时算 Brier，与模型做同口径对比。

**存档在浏览器本地**（localStorage），服务端保持无状态、数据快照保持只读，
容器不需要挂卷。键名统一带 `dc-nba:` 前缀——作品与主站同源，
localStorage 按源隔离而不是按路径，不加前缀会和别的作品互相冲掉存档。

### 玩家档案：为什么没有账号密码

一台设备上可以建多个玩家档案，各自独立存档、可切换、可用存档码导出到别的设备。
身份被刻意做成「这台浏览器上的一个本地档案」，理由有三条：

1. 应用部署在 `/works/` 路径下，网关中间件双向剥离 Cookie，传统会话用不了，
   只能把令牌放 localStorage——安全性反而比 httpOnly cookie 更差。
2. 服务端无状态、快照只读、容器不挂卷。加账号就要加存储卷，
   随之而来的是备份、迁移、权限一整套负担。
3. 存密码是要负安全责任的，一个展示作品不值得。

**需要强调**：不同访客用各自的设备打开，本来就各玩各的，不需要登录。
登录真正解决的只有三件事——同一个人换设备接着玩、同一台设备多人分别存档、
跨用户排行榜。前两件用多档案 + 存档码已经覆盖，第三件需要服务端存储时再上，
届时 `web/src/lib/profiles.js` 里的 id + name 结构可以直接复用。

新赛季开打后，同一套机制会切到实时结算（ingest 会把已完成比赛带进来）。

## 服务端存储与性能

排行榜需要跨用户状态，这是整个应用唯一有状态的部分。

**SQLite（`server/db.mjs`）** — 用 Node 22 内置的 `node:sqlite`，不引 `better-sqlite3`，
省掉在 alpine 容器和 Windows 上的原生编译。三条设计约束：

- **写不进去要优雅降级，不能崩。** 容器以非 root 用户（uid 1001）运行，卷若归 root
  会 `SQLITE_READONLY`。启动时会真正写一次做探测，失败则记下可诊断的原因，
  服务端继续提供只读功能，前端退回纯本地存档。
- **绝不相信客户端报上来的分数。** 客户端只提交「押哪边、多少信心」，
  得分由服务端查真实结果自己算。实测提交 `points: 999999` 会被忽略，
  服务端按 conf 0.95 算出 90 分。
- **不存密码。** 身份用随机令牌（`Authorization: Bearer`），服务端只存 SHA-256 哈希。
  部署环境的网关双向剥离 Cookie，传统会话本来也用不了。

**性能（针对约 1000 在线用户）** — 实测数据：

| 问题 | 优化前 | 优化后 |
| --- | --- | --- |
| 20000 次模拟进行时，`/api/meta` 延迟 | 469 ms | **2 ms** |
| 赛程接口出口带宽（1000 用户，10 秒/请求） | 51.6 MB/s | **4.0 MB/s** |
| 混合请求吞吐 | 392 req/s | **516 req/s** |

三层处理，顺序有讲究：

1. **先消除工作**：模拟用固定种子，同参数必然同结果，直接缓存。
   大响应连压缩后的字节一起缓存，命中时零 CPU。
2. **再挪走工作**：缓存打不中的丢给 `worker_threads`（`server/pool.mjs`）。
   注意——**把同步计算包进 Promise 并不会让它非阻塞**，事件循环照样卡住，
   只有真正的工作线程才行。
3. **最后压带宽**：brotli/gzip，赛程压缩率 92.2%。1000 用户规模下
   带宽比 CPU 更早触顶，这一行比任何计算优化都值钱。

**排行榜是显式开关。** 它会在公网收集并存储用户数据（伪匿名令牌，无密码无手机号），
所以做成 `ENABLE_LEADERBOARD` 环境变量，部署里默认 `0`——要不要上线是一条配置，
不是一次代码改动。关闭时服务端不写任何用户数据，前端自动退回纯本地存档。

**备份**：`npm run backup`（`scripts/backup-db.mjs`）。
**不能用 `cp`** ——WAL 模式下最新事务还在 `app.db-wal` 里，直接复制会拿到半截状态。
脚本用 SQLite 自己的 `VACUUM INTO`，在一致性快照上产出可直接使用的单文件，
不需要停服，也不需要容器里装 `sqlite3` 命令行。默认保留最近 7 份。

容器内的 cron 示例：

```
20 3 * * * docker exec dc-nba node scripts/backup-db.mjs >> /home/dev/work/works/dc-nba/backup.log 2>&1
```

两个会让备份**静默失效**的坑：

- **日志不要写 `/var/log/`**。那是 root 的目录，部署用的普通用户写不进去；
  而 cron 的 `>>` 重定向在命令执行之前就要打开文件，打不开则整条任务直接不跑，
  且不留任何错误。判断备份是否真的在跑，**看 `backups/` 里的文件日期，别看 crontab**。
- **镜像里只有 `scripts/backup-db.mjs`，没有整个 `scripts/`**。`ingest.mjs` 是抓取脚本，
  运行镜像里不该有它（`/api/refresh` 已关闭，抓取只在构建快照时做）。

**静态资源的缓存策略分两级**，搞错的后果很隐蔽：`index.html` 里引用的是带内容哈希的
资源名，浏览器一旦缓存住旧的 `index.html`，就会一直去加载旧的 JS——发了新版也看不到，
而且用户没有任何提示。所以 `assets/` 下的文件（名字本身带哈希）设 `immutable` 缓存一年，
`index.html` 设 `no-cache` 每次回源校验。

线程池挂掉会自动退回主线程计算，功能不因优化而失效。
`GET /api/health` 返回线程池状态、缓存条目数、内存占用，方便压测与线上排查。

## 界面

「玻璃数据终端」风格：深色底铺当前球队主色的渐变光斑，内容层是半透明玻璃卡片，
卡片顶边一条队色辉光。进入某支球队页面时整站配色随之切换。

- **官方图片**：球队 logo 取自 `cdn.nba.com/logos/...`，球员头像取自 `cdn.nba.com/headshots/...`，
  加载失败时回退到队色缩写块 / 姓名首字母，离线也能用。
- **深 / 浅主题**：侧栏切换，选择记在 `localStorage`。
- **队色可读性校正**：篮网近乎纯黑、马刺是银灰，直接当强调色会在对应主题下糊掉，
  所以按亮度把过暗/过亮的队色拉回可读区间（`web/src/lib/color.js`）。
- 背景光斑用 `radial-gradient` 而不是 `filter: blur()`——视觉几乎一致，
  但省掉三个全屏尺寸的模糊图层。

`/style-preview.html` 保留了当初三个候选方案的对比页（队色沉浸式 / 体育杂志风 / 玻璃数据终端）。

**缺阵模拟**：在球队页或预测页勾选球员即可标记缺阵，该设置全站共享，会同步影响实力榜、
赛程胜率、单场预测和赛季模拟。

**伤病名单**来自 ESPN 公开接口（NBA 官方只发 PDF 伤病报告，没有结构化接口），
随每次 `npm run ingest` 刷新，带伤处、部位与预计复出日期。
名单里会显示「缺阵 / 每日观察」徽标，侧栏有一键套用「确定缺阵」的按钮。
ESPN 用自己的球员 id，靠归一化姓名匹配到 NBA 的 PLAYER_ID（去重音、去 Jr./III 后缀），
当前 75 条全部命中。

## 预测模型

球队实力统一折算成「相对联盟平均的每场净胜分」：

```
实力 = (Elo折算分 × wElo + 净效率折算分 × wNet) / (wElo + wNet) + 阵容更迭 + 缺阵修正
分差 = 主队实力 − 客队实力 + 主场优势 + 休息修正
胜率 = Φ(分差 / 分差标准差)
```

**Elo** — 采用 [FiveThirtyEight 公开的 NBA Elo 方法](https://fivethirtyeight.com/features/how-we-calculate-nba-elo-ratings/)：
K=20，分差放大项 `((mov+3)^0.8) / (7.5 + 0.006 × 胜方Elo差)`，主场优势 100 Elo，
赛季间按 `0.75 × Elo + 0.25 × 1500` 向均值回归。中立场不给主场优势。
**赛季开打后继续吸收本赛季已完成比赛** —— 这是准确率的主要来源，见下方回测。

**净效率** — 上赛季百回合净效率 × 节奏 / 100，折算成每场分差。

**轮换影响力** — 阵容相关计算的统一基础：按**整季总出场分钟**（场均 × 出场数）降序取球员，
累计到球队整季总分钟（240 × 82）为止，累加 `(PIE − 0.085) × 分钟`，再除以 82 折算成每场。

> 必须用总分钟而不是场均分钟：垃圾时间被临时召上来的球员场均分钟可以很高
> （某队有人 6 场打了 36.2 分钟），按场均排序会把他们顶到轮换首位。

用 30 队的「上赛季名单 → 上赛季净效率」做最小二乘，得到把影响力换算成每百回合得分的系数，
**R² = 0.89**。

**阵容更迭** — 新赛季名单与上赛季名单轮换影响力之差，联盟层面做零和归一
（净效率的联盟平均恒为 0，个别球员退役不该抬高整体水位）。
**默认强度只有 0.15，因为回测证明这一项拿不出可验证的增益**，详见下方回测一节。

**缺阵修正** — 把勾选的球员移出轮换后重算影响力，空出的时间由名单里排在后面的人顶上。
下限为 0：替补顶上最差也就是持平，缺人不会让球队变强。

**假设全员健康**（侧栏开关）— 新赛季名单的分钟口径。默认沿用上赛季实际出勤，
但这会埋没上赛季伤停的球星：塔图姆只打了 16 场、字母哥 36 场、恩比德 38 场、库里 43 场，
全联盟有 14 名 PIE ≥ 0.13 的主力属于这种情况。开启后改用 `场均分钟 × 70 场` 估算，
只对上赛季出场满 10 场的球员生效——否则垃圾时间打几场高分钟的临时工会被误当成主力。
两种口径都不改动上赛季基准（它必须解释上赛季的真实净效率），
所以是两个可对照的情景，而不是一个藏起来的启发式规则。

> 实例：默认口径下凯尔特人排第 15、预计 41.4 胜；开启后升到第 6、48.5 胜。

**休息修正** — 背靠背 −1.1 分，休 2 天 +0.35 分，休 3 天及以上 +0.5 分。

**比分** — 由双方进攻/防守效率对位（`己方进攻 + 对手防守 − 联盟平均`）与节奏推出总分，
再按预期分差拆分成两队得分。

**赛季模拟** — 每次模拟先给每队抽一个标准差 2 分的实力扰动（代表赛季前评估本身的误差），
再逐场按胜率抽样。默认 3000 次。

模型参数（主场优势、Elo/净效率权重、休息强度、缺阵强度、阵容更迭强度、分差标准差、
是否假设全员健康）都可以在「比赛预测 → 模型参数」里实时调整，调整后全站生效。

## 回测：模型到底准不准

`npm run backtest` 在历史赛季上逐场重放预测。做法是对每个被测赛季只用开赛前
能拿到的信息建立初始评级，然后按日期顺序逐场预测——预测记录完成后才用真实
结果更新评级，不存在信息泄漏。

2022-23 ~ 2025-26 共 **4920 场**：

| 模型变体 | 胜负准确率 | Brier | LogLoss | 分差 MAE |
| --- | --- | --- | --- | --- |
| 评级冻结在赛季前（旧版行为） | 61.38% | 0.2351 | 0.6642 | 11.67 |
| ＋赛季中滚动更新 Elo | 64.19% | 0.2199 | 0.6300 | 11.14 |
| **＋滚动更新，纯 Elo（当前默认）** | **66.32%** | **0.2136** | **0.6154** | **10.91** |
| 基准线：永远选主队 | 55.59% | 0.4440 | — | — |

分阶段看，旧版模型随赛季推进不断退化，而滚动更新版一路走高：

| | 赛季初 (<10场) | 赛季中 (10-40场) | 赛季末 (≥40场) |
| --- | --- | --- | --- |
| 评级冻结 | 64.21% | 62.32% | 59.98% |
| 滚动更新纯 Elo | 65.33% | 65.40% | 67.24% |

隔离对照说明**这 5 个百分点全部来自"赛季中学习"，与权重配比无关**：
在评级冻结的前提下，纯 Elo (61.42%)、Elo+净效率混合 (61.38%)、纯净效率 (61.10%)
三者几乎没有差别。所以默认权重改成了纯 Elo，净效率滑块保留但默认为 0。

### 阵容更迭修正：一个被回测否掉的功能

把阵容更迭项也纳入回测后，结论是**它无法证明有价值，而原来的默认强度是有害的**：

| 阵容更迭强度 | 胜负准确率 | Brier |
| --- | --- | --- |
| 0（不启用） | **66.32%** | 0.2136 |
| 0.15（当前默认） | 66.16% | **0.2133** |
| 0.27（理论最优） | 65.96% | 0.2141 |
| 0.4 | 65.61% | 0.2160 |
| 0.8（曾经的默认） | 63.86% | 0.2262 |

诊断（30 队 × 4 赛季 = 120 个样本）：

- 更迭预测值与球队实际净效率变化的相关系数 **r = 0.229** —— 方向是对的，
  但只解释约 5% 的方差。
- 预测值标准差 4.19 分/场，实际变化标准差约 5.0。按最优线性预测，
  权重应该是 `r × σ实际/σ预测 ≈ 0.27`，而应用原本用的是 **0.8，超了约 3 倍**。
- 系统性偏差：名单里「上赛季无 NBA 数据」的球员平均占 19.5%，
  它与更迭预测值的相关系数是 **−0.213** —— 新秀多的重建队被系统性判为变弱。
  这是信号被稀释的主要原因之一，要修需要引入选秀顺位先验。

所以默认强度从 0.8 降到 0.15（该权重下 Brier 最优，但相对不启用的增益仍在噪声内）。
界面上的「阵容更迭」列继续展示，滑块可调，但**不要把它当成已验证的准确率来源**。

需要说明的是，这个测试对该功能是偏宽容的：历史赛季的名单接口返回该赛季全程名单，
含交易截止日才加盟的球员，用来预测赛季初的比赛存在轻微信息泄漏。
连这个乐观上界都测不出增益。

回测数据缓存在 `data/history/`，重跑不会重复抓取。

## 已知局限

- **新秀与海外新援按替补级计算。** 他们出现在名单里，但上赛季没有 NBA 出场记录，
  总分钟为 0，既不占轮换时间也不贡献实力。对手握高顺位新秀的重建队，模型会偏保守。
- **上赛季伤停的球星在默认口径下被低估**，用侧栏的「假设全员健康」切换情景；
  该开关无法区分"伤愈复出"与"确实会继续缺阵"，只是给出乐观一侧的边界。
- **PIE 低估无球防守与组织牵扯。** 防守型球员的价值会被算低，个别首发的「缺阵影响」
  甚至显示 ≈0（PIE 低于替补级基准）。
- **球星缺阵损失落在 8~12 分区间**，与博彩市场对 MVP 级球员的盘口变动大体一致，
  但 PIE 无法区分「高出场量」和「高价值」，出场时间极多的非超巨会被高估。
  可以调低「缺阵影响强度」。
- 赛季中被交易的球员，其整季分钟全部计入最后效力的球队。
- 赛季模拟的分区排名用随机数打破平局，未实现 NBA 官方的相互战绩等平局规则。
- 阵容更迭修正已纳入回测并被否掉（见上），默认强度降到 0.15。
- **缺阵修正仍未被验证**：回测需要逐日的历史伤病名单，ESPN 接口只给当前状态、
  不提供回溯查询，因此这一项的增益无法量化。它的量级不小（约基奇缺阵 −11.9 分），
  是模型里最大的未知数，使用时请自行判断。
- 伤病数据是抓取时的快照，不是实时的。赛季中要保持准确需要重新跑 `npm run ingest`。
- 休赛期抓到的多是赛季前手术记录（带较远的预计复出日期），赛季开打后才会反映真实出勤。
- NBA 杯淘汰赛（6 场）为待定对阵，不参与模拟；因此每队排定场次为 80 场而非 82 场。

## 项目结构

```
scripts/ingest.mjs      抓取并归一化数据 → data/*.json
scripts/backtest.mjs    在历史赛季上回测模型准确率
scripts/backup-db.mjs   备份排行榜数据库（VACUUM INTO，不能用 cp）
scripts/check-jsx.mjs   检查 JSX 组件引用，接在 build 前面
server/
  nbaClient.mjs         stats.nba.com 客户端（浏览器请求头 + 串行限速 + 重试）
  espnClient.mjs        ESPN 伤病接口客户端（含姓名归一化匹配）
  db.mjs                SQLite 存储（玩家、预测、排行榜）
  pool.mjs              工作线程池 + 结果缓存 + 预压缩缓存
  worker.mjs            计算工作线程
  replay.mjs            逐日重放，生成对赌题库
  ratings.mjs           Elo 计算、轮换影响力与回归拟合
  predict.mjs           预测引擎（单场预测、赛程批量、赛季模拟、实力榜）
  teamMeta.mjs          30 队中文名与队色
  index.mjs             Express API + 静态资源托管
web/src/                React 前端（极简 hash 路由，无额外路由库）
data/                   抓取产物（已 gitignore）
```

## API

| 接口 | 说明 |
| --- | --- |
| `GET /api/meta` | 赛季信息、默认参数、数据量 |
| `GET /api/teams` · `GET /api/teams/:id` | 球队列表 / 球队详情（含阵容、转入转出、带预测的赛程） |
| `GET /api/players?teamId=&onRoster=1` | 球员数据，附 `outCostPts`（缺阵影响）与 `injury`（伤病状态） |
| `GET /api/injuries` | ESPN 伤病名单快照 |
| `GET /api/schedule?type=&teamId=&from=&to=&limit=` | 赛程（默认带预测，`predict=0` 关闭） |
| `GET /api/rankings` | 实力榜 |
| `POST /api/predict` | 单场预测 `{homeId, awayId, gameId?, neutral?, out?, params?}` |
| `POST /api/simulate` | 赛季模拟 `{sims?, out?, params?, seed?}` |
| `POST /api/refresh` | 重新抓取数据并热加载（生产环境用 `ALLOW_REFRESH=0` 关闭） |
| `GET /api/health` | 线程池 / 缓存 / 内存 / 数据库状态 |
| `POST /api/players` | 创建玩家，返回一次性令牌 |
| `GET /api/me` · `POST /api/me/name` | 用令牌确认身份 / 改名 |
| `POST /api/picks` | 同步预测，得分由服务端计算 |
| `GET /api/leaderboard?mode=&min=` | 排行榜（10 秒缓存） |

GET 接口可用 `?out={"teamId":[playerId]}`（JSON 字符串）传入缺阵名单，
以及 `?homeAdv=3&wElo=0.6&turnoverWeight=0&assumeHealthy=1` 等参数覆盖。

## 数据更新

新赛季开打后重新抓取即可自动切换基准赛季：

```bash
npm run ingest
# 或指定赛季
PRIOR_SEASON=2026-27 TARGET_SEASON=2027-28 npm run ingest
```

数据来源为 NBA 官方 stats.nba.com，仅供个人学习研究使用。
